# 更正清单 —— 本会话被推翻的结论

> 这一份可能是整个文件夹里最有用的东西。它记录的是**看起来合理、实际是错的推断**，
> 以及每次是被什么推翻的。目的是让下一个分析者不必重走。
>
> 前四次里有两次是被我自己的复核推翻的，两次是被使用者指出来的。
> 2026-08-28 纳入 hstarpre 后新增更正 #5。

## 更正 #1 —— "模板是 deck 的有损压缩，生成器表达不了 RC"

**当时的推断**：往返矩阵显示 21 个算例无一能往返，`ikindks 5→0`、`elem_index 25→1`、
材料属性被换成默认值。结论是生成器的 schema 太窄，表达不了稀有耦合。

**被什么推翻**：我自己的复核。做了第二个实验——**跳过导入器**，直接用算例自带的
人工 `config.json` 生成，结果 `train01` 六个文件**逐字节等价**，其余算例只差 1~5 行
且全部是当次有意做的改动。

**真相**：生成器是精确的，**缺的是导入器**。Mode C 的两半（`import_glb` 与
`generate_all`）从来没有对接过。

**教训**：一个"全表都失败"的测量结果，先怀疑测量本身。

## 更正 #2 —— 往返矩阵的第一版数据全部作废（我自己的 bug）

**当时的推断**：第一版矩阵显示的巨大偏差被当成能力缺口的度量。

**被什么推翻**：复核测量脚本时发现，`import_project` 返回
`{"config": …, "summary": …}` 包装层，而我把**整个包装层**喂给了 `generate_all`。

**这个 bug 的恶劣之处**：它**不报错**。每个键都落空，deck 按全默认值生成——
而"全默认值生成的 deck"与"schema 表达不了这个算例"在结果上**完全无法区分**。

**真相**：修正后重测，`.pre` 忠实 2/21、`.LOA` 忠实 4/21（而非全部失败）。
据此修导入器后达到 `.pre` 21/21、`.LOA` 15/21。

**教训**：**静默降级是最难发现的 bug 形态**，而这正是整个 HSTAR 工具链的主要失败模式——
本 bug 与它诊断的对象是同一种病。

## 更正 #3 —— `.LOA` 的"第二种方言"（连错两次，方向相反）

**第一次推断**：5 个算例（`train_contact_nonlinear` / `train_seepage` /
`train_seepage_stress` / `train_slope_unknown` / `train_vie_boundary`）使用
`'TIME CURVE in each BLKS'` 格式，每块一份时间曲线表。判定为"第二种方言，
config schema 只有一份全局 `time_curves`，表达不了，显式拒绝"。

**第二次推断**（修正第一次）：源码里 `.loa` 有两个 reader
`external_load_1` / `external_load_2`。所以"不是方言，是两个 reader，
走哪个由开关决定"。

**两次都错。**

**被什么推翻**：调用点的循环上下文分析。

```
Fem.f90:1672  call external_load_1        ← 循环外,只调一次
Fem.f90:1673  do iblks = lblks+1, runblks
Fem.f90:1886    call external_load_2      ← 循环内,每块一次
```

**真相**：两个 reader **不是二选一，是一前一后**。
`external_load_1` 读曲线表+点载+边定义（一次），
`external_load_2` 读每块的边荷载+体力+`tcurvegravity`+梁载+板载（每块一次）。
**没有任何开关在它们之间做选择。**

**那 5 个文件到底是什么，仍未定**（见 `06-open-questions.md`）。
按当前源码它们读不通——第二块的曲线表会撞进 `external_load_2` 的
`edge_load_group, delgroup`。但它们都有 `1.flavia.res`，说明历史上跑通过，
而且**都不在 15 个基准套件里**，从未被当前求解器验证过。
最可能的解释是**旧格式，早于 `external_load_1/_2` 的拆分**。

**教训**：`grep` 到两个 reader 就断言"二选一"，是把**存在**当成了**选择**。
调用点的循环/守卫上下文和 READ 语句本身同等重要。

## 更正 #4 —— "不要重做 deck 格式"

**当时的推断**：看到 `Easy_HSTAR` 是 76,403 → 29,866 行的求解器重写 + 200+ 参数
TOML，判定"复杂性住在 dispatcher 里，任何不表示 dispatcher 的格式只是把它藏起来，
所以不要重做格式"。

**被什么推翻**：使用者指出——不重做格式意味着手工填写始终极其复杂，
整个系统也不优美；而现代化输入本来就是 `Easy_HSTAR` 的初衷。

**这个反驳是对的，我的推论有一步跳跃**：我反对的是**扁平的 200 参数表**，
却把它当成了"现代化输入格式"的全部。不是。

**真相**：扁平表恰恰是反面典型。**把 dispatcher 显式化的那个格式，
比现在的 deck 更优美，不是更复杂**——因为它消灭了"这 200 个字段里哪些跟我有关"
这个问题。见 `04-proposal-input-format.md`。

`Easy_HSTAR` 的初衷没错，问题在于把**两件独立的事**绑在了一起：
新输入格式 + 重写求解器。前者可以单独做，而且能做在已验证的 YL 主线上。

**教训**：反对一个具体实现时，检查自己是不是顺手反对了它想达成的目标。

## 横向观察

前四次更正里，**三次的错误形态是同一个：把"我观察到的那一条路径"当成了全部。**

- #1 把"导入器路径失败"当成"生成器不行"
- #3 把"存在两个 reader"当成"二选一"
- #4 把"一种现代格式的实现"当成"现代格式这个想法"

这与 HSTAR 本身的问题同构：**一个 deck 文件被多个 reader 消费，
你看到的样例只展示被走过的那一条，而且不会告诉你还有别的路径存在。**

## 更正 #5 —— `.ifs` 的四段顺序写反

**原结论**：`stiff_ifs2006 / ifsnedge` 是 `.ifs` 第一段，随后才是流固界面、
流体吸收和固体吸收。

**被什么推翻**：纳入 `_archive/hstarpre` 后，用其 producer 顺序反查当前求解器顶层调用点。
`hstarYLOrig/HSTAR/Fem.f90:200-203` 明确依次调用：

```
stiff_interface_fluid_solid
stiff_absorb_fluid
stiff_absorb_solid
stiff_ifs2006
```

`_archive/hstarpre/sourcef90/fempre.f90:5766-5777`（位于 `prepare_ifs_file`）也依次写
`nifsgroup / nabsgroup / nabssgroup / ifsnedge`。历史生成结果中的 `1.ifs` 同样如此。

**真相**：正确顺序是流固界面 → 流体吸收 → 固体吸收 → ifs2006。
`nabsgroup` 只是 hstarpre 写出的标签文本，当前求解器实际读入变量仍为 `nabsfgroup`；
因为标签被读到 `text` 后丢弃，两者不构成格式差异。

**教训**：reader 集合即使完整，也不包含执行顺序；顺序必须由调用点确认。
producer（hstarpre）与 consumer（HSTAR）的双向对照，比单看任何一边都可靠。

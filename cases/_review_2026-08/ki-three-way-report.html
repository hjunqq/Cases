三方知识闭环评估：该抄什么，该退回什么

读完三方源码后的结论是一句话：KISS 在运行时检索「领域知识」而没有运行历史；你在运行时检索「运行历史」而完全不碰领域知识。两者在这一根轴上严格互补——你的 context_load 会召回经验和基准，但从不读 docs/references/。HPC-Skills 在这根轴上什么都没有。

先更正前两版报告

这些结论此前基于 README 摘要，读到源码后有五处要改，其中两处结论完全反转。

撤回与反转

  1. 「抄 knowledge_infrastructure.yaml」——撤回。119 个包都有这个文件，但 ADCIRC 那份是 KDT 批量生成的空壳：version: auto-generated、description: ''、tools: []，每个 milestone 的 verification 全是同一句 "Output files exist and pass validation"。文件数不等于知识量。
  2. 「dag.yaml 不该抄」——反转，该抄。ADCIRC 的 dag.yaml 1000+ 行，分 identity / boundary / inputs / processes / states / outputs / influence / safety 八段。它不是执行 DAG，是模型本体论；其中 boundary.scope_in / scope_out（这个模型能算什么、明确不能算什么）是三方里独有的东西。
  3. 「KISS 仓库 404」——不成立。上一版里 agent 报的 404 是假的，gh api 列目录读文件全通。
  4. 「P0：让 KI 失败侧落数据」——问题定性错了。写入路径早就实现了：improve_router.py:147-205 的 _record_failed_attempts() 会写 failure_class / failure_signature / fix_action 并置 do_not_repeat=True。库里 13 条全空是因为这条腿从未被跑过，不是没写。正确动作是补集成测试去压它，不是去实现它。
  5. 「KISS 的 2406 条三元组都是机器可读 YAML」——不准确。ADCIRC 是结构化 diagnostics/triplets.yaml，但深度测试对象 VIC 用的是散文版 diagnostics/triplets.md。包与包之间不一致，而 SKILL.md 里两个包都写着「去查 triplets.yaml」。

今天撞到的实证

「证据弱」不是抽象批评。本次会话查出：validate_results.py:490 把 analysis_type 硬编码成 "static"，而 lookup 精确匹配 —— 所有 dynamic/modal/transient 家族的 golden 守卫从注册那天起就没跑过；同时金标准用 harness.gate 的矢量解析器写入、校验器却用只认单值行的正则读取，两边永不相等。两个 bug 叠加，让守卫静默失效数月而系统毫无感知。这正是 KISS severity: silent 这个字段要抓的失败类。

唯一值得整体照抄的东西：triplets 的字段设计

KISS 的自动生成层（KI 清单、workflow.md、preflight_check.py）都是空壳，但 diagnostics/triplets.yaml 是手写的、字段设计得极好，而且和你的 LangGraph 几乎同构。

KISS 字段 作用 映射到你这边
stage失败发生在流水线哪一阶段（s1_mesh_preparation…）直接等于你的节点名：mesh_workflow / parameter_workflow / preflight / execute / evaluate
symptom.detection_methoderror_pattern 还是 value_comparison —— 告诉机器该怎么判定命中failure_triage.py 现在只会做 error_pattern 式子串匹配；value_comparison 这类要靠 harness/gate.py 出数值证据
severity: silent标记「不报错但结果错」的一类失败最该抄的一个字段。你现有的门控只抓 crash/NaN/全零；今天那两个 bug 和「位移被加速度覆写」全属 silent 类，现在无处登记
remedy.tool_to_run修复动作直接指向一个可执行工具等于 improve_router 的 target 三选一：data_repair / mesh_workflow / parameter_workflow
remedy.prevention指向那个能让此错永不再犯的永久防护对应你「verified fix 要落 CLAUDE.md + 工具默认值 + 测试」这条既有纪律，但现在没有字段承载它

你的 docs/references/error-recovery.md 已经有 7 条 Pattern ID，结构（Symptom / Root cause / First checks / Primary fix）本来就是三元组，只差把它变成机器读得懂的格式并补上上面这几个字段。这是全部建议里设计成本最低、收益最直接的一条。

另外两件小而值钱的

  • SKILL.md 的强制执行策略前置（KISS 独有）。它把「失败时的动作顺序」写死在第一屏：查三元组 → 读官方文档 → 找跑通的样例 → 最后才改工具，并明确禁止「用简化公式替代真实模型」和「写自定义调试脚本」。你有等价纪律，但散在 CLAUDE.md 的 Guardrails 里、且全是「不要做什么」的否定句式。
  • boundary.scope_in / scope_out（KISS dag.yaml）。显式声明「这个模型能算什么、明确不能算什么」。映射到你这边是 case_family 级的能力边界——你的 capability/registry.yaml 只有 21 行、粒度停在 analysis_type，而你手上真实的边界知识（HSTAR_Q 单场温度场走 static_U 会 SIGSEGV、YL 主线 Q+UT 联立不可行）现在只活在记忆和聊天记录里。

取舍结论

自研为主干，只吸收 KISS 的知识形式化，不动运行时

三方里只有你有真正的运行时闭环：状态机重路由、经验驱动改道、求解器族血缘过期、checkpoint 续跑、人工介入中断、跨算例批调度。HPC-Skills 一样没有，KISS 声称有的那层（workflow.md / KI 清单 / preflight）读进去全是 KDT 生成的空壳。把你的东西塞进他们的目录格式是降维。

反过来，KISS 手写的那部分——triplets 字段设计、scope_in/scope_out 边界、SKILL.md 的强制调试协议——是扎实的工程实践，且与你的节点结构近乎同构，吸收成本极低、与其仓库存亡无关。

吸收

  • triplets 字段 schema，尤其 severity: silent 与 remedy.prevention
  • scope_in / scope_out 能力边界声明
  • SKILL.md 首屏的强制执行 / 调试协议
  • 「开工先跑 preflight」这个约定
  • 分阶段产物存在性续跑（比 checkpoint 轻，可作补充）

不动

  • LangGraph 编排层——三方里唯一的真引擎
  • promote_case 的运行时四层扇出，不要退回离线 KDT
  • 不为对标数字灌水 case_family
  • 不引入第二套 DAG 描述
  • 不做 KI 包双向同步

可发表性的路径不是换格式，是 P2-1 那组 A/B 数据。KISS 论文的说服力来自 3000 次试验的 84% vs 40%，不来自 YAML 长什么样。你已有 11 个 family、24 条基准、完整闭环——缺的只是把开关关掉再跑一遍对照。先出数据，再谈格式。

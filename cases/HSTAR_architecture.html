①harness — 中立共享层如何发挥作用

一个被 chat 链路(skills)和 LangGraph 链路(workflow)共同 import 的纯 Python 库 —— 配置合并、物理门控、回归基准、求解隔离的单一真相源。两条路都穿过它,结果口径不会分叉。

harness.dictmerge
deep_merge()
配置 override 的深合并规则 —— 模板 + 覆盖 JSON 如何叠加,一处定义,两条路一致。
harness.gate
physics_gate() · detect_crash_markers() · result_values()
物理门控 + 崩溃标记检测 + 结果取值 —— 判定一次求解"是否可信"的统一标准。
harness.benchmarks
get_static_benchmark() · lookup / list
回归基准 + 容差(位移/应力的黄金值)—— 结果校验与"是否回退"的唯一依据。
★ harness.sandbox
run_solver() · thread_cap()
bwrap jail + 线程闸 —— 求解执行隔离。本次 T2 新增,是 solver 唯一执行咽喉。
两条链路的接入点

chat 链路：run_pipeline → harness.sandbox.run_solver(执行);validate_results → harness.gate + benchmarks(校验)

langgraph 链路：execute 节点 → run_solver → harness.sandbox(执行);evaluate 节点 → validate_outputs → harness.gate + benchmarks(校验)

⇒ 无论走对话还是自动编排,求解的"隔离方式"和"是否通过"用的是同一套代码 —— harness 是防两条路发散的中枢。

②LangGraph — 如何编排(自愈式流水线)

一条 build → solve → validate 主线,配一个自愈环:任一阶段失败/不达标都落到 failure_triage,由 improve_router 决定恢复策略(修数据 / 重网格 / 重参数 / 提代码补丁 / 人审 / 放弃)。带 LangGraph checkpointer 与人审中断。

主线 (happy path)
START▸ intake▸ capability_gate▸ context_load▸ data_audit▸ mesh_workflow▸ parameter_workflow▸ preflight▸ execute★ harness.sandbox▸ evaluate★ harness.gate+bench▸ finalize▸ END
自愈环 · 任一阶段失败/不达标
↯ 落到 failure_triage 诊断病因 ▸ improve_router 选恢复策略：
data_repair 修输入
mesh_workflow 重做网格
parameter_workflow 重建参数
code_patch_proposal 提代码补丁(自改进)
human_review ⏸ 人审中断(interrupt)
finalize 放弃/收尾
capability_gate → 能力未注册则 failure_triage
data_audit → 输入坏则 data_repair
preflight → runnable? 否则回 mesh / data_repair / triage

evaluate → 物理门控/基准不过则 failure_triage

registries:capability / template / run / experience —— 编排中查"能不能做/用什么模板/历史怎么做的",成功经验回灌 context_load 形成少样本检索。

③workflow(:8800)与主服务(:3000)如何联动

两条独立触发路径 —— agent 在对话内主动跑经验循环,或 UI/API 直接编排批处理与人审。

关键:基础求解不碰 :8800。 一次普通对话求解走 :3000 → agent → run_pipeline → harness.sandbox → solver,与编排服务无关。:8800 只在经验循环 / 自改进 / 批处理 / 人审时介入 —— 所以它挂了也不影响日常求解。
